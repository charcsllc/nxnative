# dm/gfx/hostvk: the Vulkan backend (Windows and Linux)

The host's Vulkan backend of the Windows and Linux port, designed in [vulkan-backend.md](../../../docs/design/vulkan-backend.md). The directory is `hostvk` because `dm/gfx/vk` is the guest's Vulkan API on Metal. Apple builds never compile it: `dm/host/Makefile` and `dm/gfx/tests/Makefile` take `dm/gfx`, `nvn`, `tex`, `vk` and `gl` only.

## What exists

The core of phase P3 (design 11.1): the backend behind [nvn_be.h](../nvn/nvn_be.h), in plain C11 over [volk](../../third_party/volk/VENDOR.md), which loads the Vulkan loader at run time (nothing links against `libvulkan.so.1` or `vulkan-1.dll`). The library `nvn_vk` of [dm/host/CMakeLists.txt](../../host/CMakeLists.txt), beside `nvn_null`: a binary links one of them, and the host library `nxhost` links this one (`NXHOST_VULKAN`, on by default since step P8; `OFF` links `nvn_null`). The device comes up at the frontend's first call that needs it, as the Metal backend's does, and with no device that meets the baseline every function takes the null backend's form:

- [vk_device.h](vk_device.h), [vk_device.c](vk_device.c): `hostvk_init` makes the instance (the window's instance extensions from `front_vk_instance_extensions` when a surface is wanted; the validation layer, with synchronization validation and a debug-utils messenger that counts what it reports, when asked), picks the physical device (`device_index`, or the first that meets the baseline), checks the baseline of design 9.1 (Vulkan 1.3, the feature list, `VK_EXT_external_memory_host` with host allocations importable as pool buffers, `VK_EXT_transform_feedback`, which decision D6 makes required, `VK_KHR_swapchain` with a surface), records which optional extensions of 9.1 the device has (with a surface it enables `VK_KHR_present_id` with `VK_KHR_present_wait`, and `VK_GOOGLE_display_timing`, where present: the window presenter's vsync source), derives the level of design 3.6, makes the logical device with one graphics, compute and transfer queue (a transfer-only family is recorded for later) and fills `hostvk_caps`: the `be_caps` fields of design 1.5 and the backend's own (import alignment, allocation limit, the memory type imports get and whether it is coherent, timeline semaphores, buffer device address, the level). It logs one line, `[hostvk] device '<name>' driver <version> (<driver name>: <driver info>) Vulkan <x.y.z> level <A-D>: <missing optional extensions>`. Its log lines go to stderr with the host's `[dm] ` prefix, or to the function `hostvk_set_log` names: `LOG` (`dm/host/dm.h`) needs the generated game profile header and declares the whole host.
- [vk_import.h](vk_import.h), [vk_import.c](vk_import.c): `hostvk_import` imports a page-aligned host range as a `VkDeviceMemory` with one `VkBuffer` over it with every usage a pool address can have (`hostvk_pool_usage`) and its `VkDeviceAddress`; it refuses a misaligned range and an import past `maxMemoryAllocationCount` itself, before Vulkan is called. `hostvk_import_release` frees it.

The levels, from what the device offers (`vk_device.h` lists the dynamic states): **A** pipeline libraries, dynamic vertex input and every dynamic state of the pipeline description that Vulkan 1.3 does not make dynamic (extended dynamic state 2's logic op and patch control points, and ten states of extended dynamic state 3); **B** pipeline libraries without all of those; **C** no pipeline libraries, but dynamic vertex input or some of those states; **D** none of them. `DM_VK_LEVEL=B|C|D` makes the device as one of that level would be (what that level lacks is not enabled), so levels C and D can be measured on a level-A machine.

- [vk_backend.h](vk_backend.h), [vk_backend.c](vk_backend.c): the `be_*` functions. The device comes up on the first call that needs it (`DM_VK_DEVICE=<index>` picks it, `DM_VK_VALIDATION=1` turns validation on), `be_get_caps` reports it; with no device every function takes the null form (`nvn_null.c`'s: a `[RED]` line on its first call)
- [vk_memory.c](vk_memory.c): memory pools as imports (`be_addr`), each its own or, where the live allocations near the device's limit, shared by the pools of a granule of committed guest memory (step D2, below); the committed guest memory (`be_guest_map` / `be_guest_unmap`); the ring of the open submission (driver banks, converted indices, copied vertex streams, staging), the release of what the GPU may still be using after its fence; `hvk_buffer_make`, a buffer with a `VkDeviceMemory` of its own, for the callers that free it themselves
- [vk_alloc.h](vk_alloc.h), [vk_alloc.c](vk_alloc.c): the device memory allocator of decision D2 (step D2): the backend's own images and buffers as ranges of blocks, below
- [vk_texture.c](vk_texture.c), with the format table [nvn_fmt_vk.c](../tex/nvn_fmt_vk.c): images in the format each row's path gives (phase P7: its own, a substitute read through a mapping, a format the upload converts into, the RGBA8 decode of ASTC, depth 24 as 32-bit float); textures the CPU fills uploaded through the GPU (the compute passes `shaders/deswizzle.comp` and `shaders/astc_decode.comp` read the storage from the imported pool into the upload scratch, band after band, then a copy; textures of 64 KiB and more) or through the CPU (`tex/nvn_deswizzle.c` and the path's conversion, `tex/astc_decode.c` for ASTC), then write-protected by the dirty tracker; depth and stencil split from the guest's packing at upload and joined in copies (`shaders/ds_pack.comp`) and CPU reads; samplers (exact border colours, integer borders, nearest filtering for formats the device cannot filter linearly); views with the composed channel mapping; CPU reads (ReadTexels) from the image of a texture the GPU wrote; the texture memory counters of the resource line (every image, ASTC native and decoded with the blocks they stand for, the device-local budget of `VK_EXT_memory_budget`). Switches: `DM_VK_ASTC=native|decode` (decision D1), `DM_VK_DESWIZZLE=cpu|gpu`, `DM_VK_DEPTH24=d32f` (decision D10)
- [vk_shader.c](vk_shader.c): modules from `DM_MSL_DIR/vk-<DMSH_CHAIN_VK>/<key>.spv` and their reflection (`<key>.json`) through `nvn_refl_from_json_text`, checked against the device's capabilities
- [vk_pipeline.c](vk_pipeline.c): the four universal pipeline layouts of design 2.3 (the driver banks c0 and c2 as dynamic uniform buffers in the ring), compute pipelines, descriptor sets cached by content per submission slot, the backend's own pipelines (the clear triangle, the counter-report, predicate and quad-index kernels, and since P7 the ASTC decode, deswizzle and depth-stencil packing kernels; each kernel made at its first use)
- Pipelines without stutter (phase P5, design section 3; [vk_pso.h](vk_pso.h) says what the three share):
  - [vk_gpl.c](vk_gpl.c): the key (design 3.1: what the device cannot set dynamically, the topology class left out where one pipeline draws every class), the same for a draw and a prewarm row (`hvk_key_fill`); on levels A and B four libraries each cached by its own key (vertex input, pre-rasterization, fragment shader, fragment output), a fast link at first use, the link-time-optimized relink on the optimizing worker swapped in at the next draw; on levels C and D the monolithic pipeline; the wait of a draw at the bind, per reason, in `be_pso_line` (`DM_VK_PSO_TRACE=1` logs each with its key); the worker threads of design 3.5; the per-vendor quirk table `k_quirks` (empty)
  - [vk_cache.c](vk_cache.c): the `VkPipelineCache` on disk (design 3.4), one file per game and device named by the vendor and device IDs, driver version, cache UUID, `DMSH_CHAIN_VK` and this backend's version, in `DM_VK_PSO_CACHE` or `vk_pipeline_cache/` beside the save; framed and hashed, checked at load, one cache object per compiling thread merged for the write, copy and rename; the folder's upkeep of decision D8: `index.tsv` (each entry's size and last use, renamed over), a cleanup at start (`DM_VK_PSO_CACHE_CLEANUP`, on: entries of another chain or backend version, of this device under another driver, or unused for 90 days) and a size limit at start and after each write (`DM_VK_PSO_CACHE_LIMIT`, 512 MiB, `0` none: another version's entries first, then the least recently used; this game's own entry kept)
  - [vk_prewarm.c](vk_prewarm.c): the prewarm lists (design 3.3: the seed `pso_manifest.tsv` beside the shader map, then the device's `pso_user_vk.tsv`, `DM_VK_PSO_USER`), S, C, R and P rows in the Metal backend's order on the background workers, the prediction from the rows, and the prebuild `DM_VK_PREBUILD=1` with its progress on `front_progress`
- [vk_commands.c](vk_commands.c): submissions on a timeline semaphore with a completion thread (events, CPU-side reports), render passes (dynamic rendering, images in `GENERAL`, a full barrier between operations), the draw state, draws (indexed, instanced, indirect, indirect-count; quads, fans and restart converted; sources the GPU writes first copied or expanded on the GPU), clears, copies, barriers, syncs, counter reports, conditional rendering, transform feedback
- The native features of phase P8 (design section 6; [vk_commands.c](vk_commands.c), [vk_gpl.c](vk_gpl.c), [vk_pipeline.c](vk_pipeline.c), [vk_shader.c](vk_shader.c), [vk_device.c](vk_device.c)):
  - transform feedback (`VK_EXT_transform_feedback`): the buffers of `OP_TF_BIND` bound at each capturing draw, the capture begun and ended with the backend's own counter buffer (ended at a pass end and before any pipeline bind, which Vulkan forbids while a capture is active, and resumed after), Begin / Resume / End / Pause moving the byte offsets between it and the game's control buffer (its first 16 bytes) in GPU order, the vertex size of each buffer from the module's `XfbStride` decorations, `DrawTransformFeedback` as `vkCmdDrawIndirectByteCountEXT` over the control buffer's saved offset, rasterizer discard as dynamic state
  - geometry and tessellation stages, natively, through the stage-combination layouts of P3: layered rendering from either stage (`shaderOutputLayer` enabled where present), the patch size from the control shader's `OutputVertices` (`nvnCommandBufferSetPatchSize` is not recorded), GL's lower-left tessellation domain origin
  - counters (design 4.6): per pass segment, for the kinds being counted, a pipeline statistics query, a primitives-generated query (`VK_EXT_primitives_generated_query`) and a transform feedback stream query beside the occlusion query of P3; each NVN counter type has its own accumulator and is added up by `shaders/report.comp` in GPU order (the field and stride of its kind's results)
  - feedback draws (design 5.5): a draw whose descriptors read an attachment of its pass splits the pass when the pass wrote that attachment (the full barrier between passes; none can run inside a dynamic-rendering pass on Vulkan 1.3), and an attachment a pass only reads is stored with `STORE_OP_NONE`, so its store is no write after the reads; no per-game list (the Metal backend's `feedback_snap` is not needed)
  - lines as Bresenham lines (`VK_EXT_line_rasterization`, NVN's aliased lines; rectangular on a multisampled target), dynamic where the device has the state, else in the pipeline key; advanced blend modes reduced to the fixed-function factors of the Porter-Duff modes (the Metal backend's `adv_blend` table); indirect quads converted on the GPU (`shaders/quad_ind.comp`, array and indexed); arrays of descriptor handles (`TEXA` / `SAMPA`, `TEXD` / `SAMPD`, `TEXU` / `SAMPU` arrays) written element by element; draw-based copies (`shaders/copy.vert`, `copy.frag`) for colour formats a blit cannot convert and between two depth formats, the stencil written with `VK_EXT_shader_stencil_export`; `VK_NV_viewport_swizzle`'s dynamic state for swizzles other than a negated y (written, not run: no device here has it)
- The guest Vulkan layer of step P9a (design 8.1; [guest_vk.c](guest_vk.c), [guest_vk.h](guest_vk.h); the library `guest_vk` beside `nvn_vk`, which `nxhost` links with it): for the games that render with Vulkan, a pass-through shim in the import table (the `VK` / `VKB` entries, thunked by `dm/host/tools/gen_hle_thunks.py` like `hle_nvn.c`'s `NVN` ones; `vkGet*ProcAddr` look names up there). The game's instance, physical device, device and queue wrap the backend's device (`be_native_device`): the Tegra X1 shape of `dm/gfx/vk/hle_vk.m` (Vulkan 1.1, one queue family, three memory types on one heap), each limit the stricter of that shape and the host's, features where the shared device has them enabled (`hostvk_dev.enabled`; `vk_device.c` now also enables the 32-bit index range, gather offsets, MinLod and the dynamic indexing of descriptor arrays where present), formats and the timestamp period the host's. Memory: a driver allocation made at the first buffer bind, map or linear-image bind, device-local for the guest's type 0, host-visible and coherent for types 1 and 2, mapped once; in a host program with the x86-64 engine (`nxhost-run`, `t_vk_guest`) types 1 and 2 are instead pages of the engine's arena below 2^39 imported with `VK_EXT_external_memory_host` (`gmem_import`; every buffer and linear image is made with the host-allocation handle type, every image starts `UNDEFINED`, as external memory requires, and `PREINITIALIZED` barriers leave `UNDEFINED`), so the pointer `vkMapMemory` hands the game is guest memory: lavapipe 25.2.8 offers no `VK_EXT_map_memory_placed`, the other way (declared in the file's comment); optimal images on device-local memory of their own; linear images bound where the game says. Shaders: structural checks and two SPIR-V binary rewrites, `ArrayStride` moved from struct members onto array types and the second blend source moved from Location 1 to Location 0 Index 1 for a pipeline that blends with it; `DM_VK_CAPTURE`. Pipelines through the disk cache of `vk_cache.c`. Swapchains of host images handed to the present path (`be_ext_tex`, `be_present_ext`, now defined in `vk_backend.c`: until P4 a headless presenter copies each shown region into a buffer, `hvk_present_last`), the game's `PRESENT_SRC_KHR` turned into `HVK_EXT_LAYOUT`, the acquire paced as `hle_vk.m`'s, the present after the game's semaphores with the vi layer crop
- The guest OpenGL layer of step P9b (design 8.2, decision D5 option 1; [guest_gl.c](guest_gl.c), [guest_gl.h](guest_gl.h); the library `guest_gl` beside `guest_vk`, which `nxhost` links with it): for the games that render with NVIDIA's desktop GL through EGL (Digimon Story Cyber Sleuth, Balatro), the state machine of `dm/gfx/gl/hle_gl.m` with a Vulkan encoder on the backend's device. Its `GL` / `GLB` / `EGL` entries register in the import table (thunked by `gen_hle_thunks.py`, whose one run in the CMake rule now reads `nxhost`'s sources and both guest layers); `eglGetProcAddress` looks GL names up there, `DM_GL_STUBS=1` gives the others a reporting stub. Shaders from the SPIR-V library `dm/gfx/tools/gl_shaders.py --vk` writes (`<DM_MSL_DIR>/gl-vk/`: `gl_<key>_v.spv` / `_f.spv` and the Metal library's table; the fragment stage's resources in descriptor set 1, GL's clip z mapped by the shader), found by the hash of the source and the stage; varyings matched by name at the link (the fragment inputs' locations rewritten). Per frame two command buffers (uploads into textures the frame has not read yet first) submitted at `eglSwapBuffers` with the layer's timeline semaphore; dynamic rendering, images in `GENERAL`, full barriers, Vulkan 1.3's dynamic states set per draw, pipelines through the disk cache; the default uniform block per draw in transient memory as a dynamic uniform buffer; a vertex binding per input; buffers in host-visible coherent memory (small ones from slabs), persistent maps and timeline fences; what the game sees of host memory in the x86-64 engine's arena below 2^39 (`guest_gl.c`, "Memory the game sees"): each slab and each larger buffer arena pages imported with `VK_EXT_external_memory_host` (`hmem_make`, through `hostvk_import`; a refused or non-coherent import gets the driver's mapping with a red line), the strings of `glGetString`, `glGetStringi` and `eglQueryString` arena copies, the fence objects garena blocks, the EGL handles opaque host values (`t_vk_guest_gl` checks the mappings, strings and a fence below 2^39); images bottom row first with a positive viewport and the winding reversed, and the headless presenter copying the rows bottom up under `be_set_origin_lower_left` (`vk_backend.c`); the window surface three images through `be_ext_tex` / `be_present_ext` plus a depth-stencil image. `guest_gl_shutdown` releases the layer's objects (its test, before the backend's shutdown)
- The window presenter and the vsync source of step P4a (design 7.2 to 7.4; [vk_present.c](vk_present.c), [vk_present.h](vk_present.h)): with a Vulkan window that the host program registers (`hvk_present_set_window`: `front_sdl.c`'s `front_vk_create_surface` and `front_vk_pixel_size`), the device is made with `VK_KHR_swapchain` and `be_present` (NVN frames) and `be_present_ext` (the guest layers' frames) go to it; without one, or with `DM_VK_HEADLESS=1`, to the headless presenter of `vk_backend.c`, which now takes NVN frames too. A present copies the frame's region (the layer crop) raw into a snapshot image of the presenter on the backend's queue (an sRGB frame into its UNORM twin, so its stored bytes reach the screen), and its ticket is that copy, so the game's texture is free once it is done; the present thread makes the surface at the first frame (until then the front end's progress screen keeps the window), then for each snapshot acquires a swapchain image, clears the letterbox black, blits the snapshot into the centred rectangle that keeps its aspect (bilinear, nearest at one to one, flipped under the lower-left origin) and presents. The swapchain: a UNORM format of 8 or 10 bits in `SRGB_NONLINEAR`, at least three images, FIFO, `DM_VK_PRESENT_MODE=mailbox` for MAILBOX (decision D12; IMMEDIATE is not offered), remade on `VK_ERROR_OUT_OF_DATE_KHR`, `VK_SUBOPTIMAL_KHR` or a new size from the front end where the surface has no current extent (Wayland). A present that finds every snapshot queued for 100 ms (a hidden window, a stuck surface) drops its frame rather than hold the game. The vsync source: a thread of 60 Hz ticks (`be_vsync_*` with the display link's contract, and `be_vsync_wait_vsync` for `hle_sdk16.c`'s vsync event), phase-locked to the screen at a multiple of 60 Hz by when presents reached it (`VK_KHR_present_wait`, polled by a waiter; else `VK_GOOGLE_display_timing`'s actual present times; else the return of a FIFO acquire that waited), and `be_presented_time` from the same; `hvk_win_readback` / `hvk_win_last` read back the swapchain images for the tests
- The spatial upscaler at present of step D4 (design 7.4, decision D4; [vk_present.c](vk_present.c), "Scaling"): `DM_PRESENT_UPSCALE=fsr` runs AMD FidelityFX Super Resolution 1.0 ([dm/third_party/fsr1](../../third_party/fsr1/README.md), v1.0.2, unmodified; the wrappers [shaders/fsr_easu.comp](shaders/fsr_easu.comp) and [shaders/fsr_rcas.comp](shaders/fsr_rcas.comp)) as two compute passes in the present thread's command buffer, after the snapshot copy and before the swapchain image's present barrier, so the game's thread never waits for them: EASU samples the snapshot (linear, clamp to edge, the lower-left origin's rows mirrored in the shader) into an R8G8B8A8_UNORM image of the picture's rectangle, remade on a new size; RCAS sharpens it (`DM_PRESENT_SHARPEN`, in stops, default 0.2) into the swapchain image itself where the surface takes storage writes and the shader can name its format (`rgba8`, or any format with `shaderStorageImageWriteWithoutFormat`; the swapchain is then made with `STORAGE` usage, only in this mode), else into a second R8G8B8A8_UNORM image blitted one to one. Both passes filter the stored bytes as UNORM values: the picture's own gamma space, as FSR 1 expects. FSR 1 only upscales: at one to one and below, the blit. `metalfx` selects FSR 1 (one log line); `integer` blits nearest at the largest whole multiple that fits, centred, the border black, and blits as before when none fits. A device without the features (the snapshot's format not filterable, R8G8B8A8_UNORM not sampled and stored, no pipeline) gets one red line and the bilinear blit
- [shaders/](shaders): the backend's GLSL; `shaders/gen_spirv.sh` writes the SPIR-V headers of `shaders/gen/` and of the GPU tests (`dm/gfx/tests/vk/shaders/gen/`), committed, so building needs no glslang

Declared with a `[RED]` line, for later phases: the swapchain image count from the game's own window texture count (D12), a present pass that filters an sRGB frame's bytes in gamma space as Metal's `present_raw_src` view does (the blit and the upscaler filter the UNORM snapshot, which is the same), the Linux compositor's presentation feedback and DXGI's `WaitForVBlank` as vsync sources where neither present wait nor display timing exists (design 7.3; the source's clock runs free then), the Metal backend's DM_CTL diagnostics (`dm_gfx_shot_at`, texture and pass dumps) (P4); GPU conversions of indices other than quads without restart (P4); the live look-ahead prediction over the rest of a submission (design 3.3), pipeline libraries on a device without fast linking or independent interpolation decorations (the interpolation-matched vertex variants of 3.2), points on a device without `VK_KHR_maintenance5` (P5); discrete-GPU mirrors (P6); the other options of decision D1 (RGBA16F, BC7 at upload, BC7 cached), texture → buffer copies of a decoded ASTC texture and buffer copies of a texture whose upload converts on the CPU, render targets held in a substitute read through a mapping or in a converted format, a constant depth bias on depth 24 held as float without `VK_EXT_depth_bias_control`'s float representation (P7); the GL layer as an external producer (design 8.2, decision D5). Declared by the guest Vulkan layer (step P9a): sparse binding, features a game enables that the shared device was not made with (`robustBufferAccess` is not enabled: it costs NVN games), vertex formats the host cannot fetch, a game destroying a swapchain image. The vi layer crop and size come from `dm/gfx/hle_vi.c`, part of `nxhost` on the port as on Apple (`t_vk_guest` and `t_vk_guest_gl` link it and set them through its `vi::SetLayerCrop` and `vi::CreateLayer`); `vkGet*ProcAddr` and `eglGetProcAddress` return the host function, which the x86-64 engine's thunk of the entry hands the guest at its guest-visible address (a function pointer return, `dm/host/tools/gen_hle_thunks.py`; `dm/host/aot.h` `dm_guest_fnptr_named`), and `DM_GL_STUBS`'s stubs become the engine's stubs of the names asked for. Declared at step P8, because the frontend does not record the state (its record format is the Metal backend's too, so it stays) or no device here can run the path: the alpha test (`nvnCommandBufferSetAlphaRef` is only logged; the translator has the test off), line widths other than 1 (`SetLineWidth` is only logged), the patch size and the fixed-function tessellation levels (`SetPatchSize`, `SetInner / OuterTessellationLevels`: a program without a control shader is skipped), depth bounds (`SetDepthBounds` is a no-op), conservative rasterization and sample locations (only logged; lavapipe has neither extension), conditional rendering for the profiles without `render_cond` (`hle_nvn.c` records `SetRenderEnable*` only behind that key), advanced blend modes other than the Porter-Duff ones (`VK_EXT_blend_operation_advanced` is not used: lavapipe lacks it), viewport swizzles other than a negated y on a device without `VK_NV_viewport_swizzle` (a vertex-stage swizzle is the shader chain's, P2), the counter types Vulkan has no query for (`TESS_EVALUATION_SHADER_PRIMITIVES`, `ZCULL_STATS`: zero counts), indirect draws with restart, line loops or 8-bit indices a device cannot take, copies between an integer and another class, of 3D or multisampled textures that a blit cannot do, geometry streams other than 0 for rasterization, the provoking vertex. Not here: the idle thread class of design 3.5 (the platform layer's lowest is `UTILITY`) and the frame step's slack for the optimized relinks (with the presenter, P4).

**Device memory (decision D2, step D2).** Drivers limit the live `VkDeviceMemory` objects (`maxMemoryAllocationCount`: 4,096 on NVIDIA and AMD under Windows; lavapipe has no practical limit) and a game makes thousands of textures and buffers, so the backend's own images and buffers (textures, the dummies, the ring's chunks, the upload scratch, staging and readback buffers, the counters' and the draw helpers' buffers, the shaders' constant banks and 64 KiB constant windows, the support and zero banks, the presenters' images and buffers) and the guest layers' (the guest Vulkan layer's images, the guest OpenGL layer's textures, transient and readback buffers) are ranges of blocks from [vk_alloc.c](vk_alloc.c), an allocator of our own in C. A block is 64 MiB in a device-local memory type and 16 MiB in any other, at most an eighth of its heap; a host-visible block is mapped once and a range's pointer is the block's plus its offset. A resource larger than half a block, or one whose driver prefers or requires an allocation of its own (`VkMemoryDedicatedRequirements`), gets one, with `VkMemoryDedicatedAllocateInfo`. Within a block: best fit over the free ranges, the resource's alignment, and a page of `bufferImageGranularity` between a linear range (a buffer) and an optimal one (an image), checked against the neighbours of the free range a resource is cut from; in a host-visible type without `HOST_COHERENT` every range is on multiples of `nonCoherentAtomSize`, and `hvk_mem_flush` / `hvk_mem_invalidate` widen their range to it. A range given back joins its free neighbours; a block left empty goes back to the driver after 8 more submissions (`HVK_ALLOC_GRACE`), or at once when the count is at the limit. Each block and each allocation of its own takes one of the limit (`hostvk_dev.allocations`, shared with the imports, the guest layers and `hvk_buffer_make`); a refusal for the count logs a `[RED]` line with the counts; the device line gives the limit and each type's block size, the shutdown line (`[hostvk] device memory at shutdown:`) the peak blocks and bytes, the bytes in use, the waste, the own allocations, the live allocations' peak and the pool imports. What the GPU may still use goes back through `hvk_defer` as before, now with its range. Imports stay one allocation each, but once the live allocations reach half the limit a pool inside one 64 MiB granule of committed guest memory joins the import of that granule's committed range (design 4.2's coalesced imports; `be_guest_map` records what the host commits); a decommit beside the pools of a shared import moves them to new imports first. Still one allocation each, outside the allocator: the imports (pools' own, the guest OpenGL layer's slabs and large buffers in the x86-64 engine's arena: they are the game's pages), the guest Vulkan layer's memory for the game's own `vkAllocateMemory` calls, and `hvk_buffer_make`, which only the GPU tests call now. A shader's constants (c1: its reflection's bytes, 256 to 768 in the libraries so far, 6 KiB at most) are packed as the Metal backend packs them (`nvn_mtl.m` `c1_store`; [vk_shader.c](vk_shader.c) `c1_make`): a shader whose c1 indices are proven bounded goes into a shared bank of 4 MiB (a host-visible range of a block), at an offset aligned to 256 bytes (or `minUniformBufferOffsetAlignment` if larger), its data followed by zeros to the end of its span (the data rounded up to 256 bytes, plus 256), and a bank takes no shader whose span would leave less than 64 KiB after it, so every c1 descriptor (the bank's buffer, the shader's offset, 64 KiB; `vk_pipeline.c` `build_set`) lies inside the bank and the bank ends in 64 KiB of zeros; the shader's own view of c1 (its SPIR-V, its indices) is unchanged. Proven bounded means not listed in the profile's `c1_full_vk.tsv`, which a full `dmsh_build_vk.py` run writes with `c1_guard.py` (the rule of the Metal chain's `c1_full.tsv`: every c1 index proven to stay inside that span) on the analysis MSL rendering of the library's own SPIR-V (geometry and tessellation shaders, which have none, listed); the backend reads it beside the shader map as `nvn_mtl.m` reads `c1_full.tsv`, only when its first line names this library's chain (`vk-<DMSH_CHAIN_VK>`) and the inputs digest of its stamp (`inputs.tsv`). A listed shader gets 64 KiB of its own (zeros after its bytes, as the Switch reads past a constant bank's data), and so does every shader when the table is missing or stale, with one `[RED]` line naming the table and why. Metal prints that line when it loads the shader map; here it comes at the first shader with a c1 that falls back to a window of its own, since a library whose shaders have no c1 (the GPU tests', the built-in kernels) needs no table and loses nothing without one. The shutdown line `[hostvk] c1 banks: <n> shaders packed in <b> banks (<bytes>), <m> with 64 KiB of their own (<bytes>)` gives the counts; shaders are unloaded only at shutdown, which gives every bank and window back. For 3,000 loaded shaders of 512 bytes, the banks take 4 MiB instead of 188 MiB [A: from the rule; to measure on a game's stamped library]. `DM_VK_MAX_ALLOCATIONS=<n>` lowers the limit (a test switch: lavapipe as a limited driver). The open submission's fence (`vk_commands.c` `g_open`) is an atomic with sequentially consistent stores and loads, cleared after the committed fence is published, so an object unpublished on one thread is never released under a submission the submit thread is recording.

CTest sets `VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/lvp_icd.json` and `VK_LOADER_DRIVERS_SELECT=lvp*` (lavapipe only) and `VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation`. ## What the backend's tests found on lavapipe

- A `DEPTH16` clear stored one unit off a fragment writing the same depth for 7 of `t_vk_depth16_clear`'s 1,042 depths: lavapipe rounds a fragment's float product half to even and converts a clear value in double. `hvk_depth_clear_value` (`vk_commands.c`) quantizes a `DEPTH16` clear as the fragment does and moves it a quarter unit inside that value's bin, for every clear path ([rendering.md, Depth16 load-clears match fragment writes](../../../docs/reference/rendering.md#depth16-load-clears-match-fragment-writes)).
- The validation layer 1.3.275 rejects the KHR names of `VK_KHR_index_type_uint8`, `VK_KHR_calibrated_timestamps` and `VK_KHR_vertex_attribute_divisor` (promoted in header 1.3.280 with the same structures and values): under an older layer the device enables the EXT names where it has them.
- A pipeline with no colour attachment must not declare the colour blend states dynamic (no `vkCmdSetColorBlend*EXT` call can name an attachment); a pipeline with the patch size dynamic needs it set before every draw.
- The pipelines of the two phases and of the four levels give the same bits: `t_vk_gpl_identity`'s 90 draws through fast-linked, optimized, level-B, level-C and level-D pipelines are bit-exact, so the quirk table has no row (design 3.2, risk 7).
- Levels C and D had never run before phase P5: forced with `DM_VK_LEVEL`, a pipeline without vertex bindings declared the binding stride dynamic, which no draw can set (VUID-vkCmdDraw-pStrides-04913), and a point pipeline whose vertex stage writes no `PointSize` failed VUID-VkGraphicsPipelineCreateInfo-topology-08773. Strides are dynamic only with bindings now; `VK_KHR_maintenance5` is enabled where present (an unwritten point size is 1.0, NVN's default). The 13 GPU tests of P3 pass on levels B, C and D as on A.
- The colour state of a target that does not blend was keyed with NVN's reset values (ONE / ZERO), which a prewarm row holds as zero, so on level D no row matched its draw; `hvk_key_fill` normalizes it, as the Metal key's `pso_key_norm` does ([Pipeline keys omit unused colour state](../../../docs/reference/shaders.md#pipeline-keys-omit-unused-colour-state)).
- `t_vk_prewarm` and `t_vk_pipeline_cache`, a synthetic list of 206 lines and 12 pipelines: no listed pipeline's draw waits after the prewarm, background or prebuild, cold or warm, level A or D; a pipeline outside the lists waits once (0.6 ms at the most on level A, 1.8 ms on level D) and not at the next start, which prewarms it from `pso_user_vk.tsv`.
- `t_vk_descbench`, 4,900 draws a frame (medians of 20 frames): cached sets with dynamic offsets record a frame in 2.1 ms (435 ns a draw, 161 descriptor writes, 56 set allocations), push descriptors in 3.7 ms (747 ns a draw, 24,500 writes); the frame takes 130 to 140 ms on lavapipe either way. The backend keeps the cached sets; the RTX 4060's numbers decide it for good (P4).
- Phase P7 (textures): an NVN sampler with linear filters on an integer texture (or a float format the device cannot filter) failed VUID-vkCmdDraw-magFilter-04553 (99 messages in `t_vk_formats`' first run): such a texture's descriptor now takes the same sampler filtering nearest (`HVK_CLS_NO_LINEAR`). The D24 ↔ float conversions of the depth-24 substitute were first written in float arithmetic, which rounds twice (`0.75 × 16777215 + 0.5` gave 12582912 instead of 12582911): they are integer steps now, exact for all 2^24 values both ways (`depth_of24`, `z24_of`, and the same in `shaders/ds_pack.comp`). Lavapipe's own findings, recorded and not worked around: its sRGB decode is up to 0.3 of an 8-bit unit off the formula (within the format's latitude); its float → `A2B10G10R10_SNORM` write does not round-trip (a 10-bit component one unit off, the 2-bit alpha -1 stored as 0); a constant depth bias of 16 units moves D24 depth by 17 steps of 2^-24 (16 on the float substitute with the float representation, 16 and 8 at depths 0.7 and 0.3 without it). On this machine the GPU deswizzle of 16 MiB takes 32.3 ms and the CPU one 32.7 ms: lavapipe runs the compute pass on the CPU, so this is not a GPU number.

- Phase P8 (native features): lavapipe 25.2.8 crashes (a segmentation fault in its queue thread) when `vkCmdEndTransformFeedbackEXT` is given a counter buffer for a transform feedback buffer that is not bound: it reads the stream-output target of every counter it is given. The backend gives counters for the bound buffers only (the Vulkan specification does not forbid the others). A draw that only reads its pass's depth attachment (tested, not written: soft particles) made synchronization validation report a write after read, the attachment's store after the draw's sampled read, with no barrier possible inside the pass: such a pass stores what it only reads with `STORE_OP_NONE` (core in 1.3), and a later draw or clear that writes it splits the pass again. Two capturing pipelines in one pass (the capture ended into its counters before the second pipeline's bind and begun again from them) gave no hazard. The tessellator's triangle counts are GL's and Vulkan's exactly: quads 2 n^2 for uniform levels and, with inner (3, 4) and outer (2, 3, 4, 5), 24 (each strip between the outer edge and the inner ring as many triangles as their segments together); triangles in concentric rings, 3 (a + b) a strip and the inner triangle for an odd level (24 at level 4, 13 at level 3, not n^2).

- Step P9a (the guest Vulkan layer): a static library's object that nothing references is left out of the link, and its import-table entries with it: a host binary gets the layer's object through the thunk table (`gen/hle_thunks.c` names every entry's C function), and `t_vk_guest` references the layer's SPIR-V checker for the same reason; without it the table had no `vk` entry. - Step D2 (the allocator): `t_vk_alloc` under a limit of 64: 300 shaders loaded through the shader path with their 64 KiB constant buffers in one block (1 allocation live); 400 buffers and 200 images in one block with 1 allocation live, where one each would have stopped at 64; 80,000 pairs of a buffer and an image in one block, none on a shared 64 KiB page (the test's granularity); 300 memory pools in 192 MiB of committed guest memory with 31 imports of their own and 3 shared by 269 pools, every pool reached by a GPU fill; 63 own allocations, then the 64th refused with the `[RED]` line. lavapipe's answers show the allocator is correct Vulkan (validation clean), not what a GPU with a real limit demands: the RTX 4060's numbers are for P4.
- Step D2 (the constant banks): `t_vk_c1`, the same 970 synthetic compute shaders (300 with 768-byte c1 segments, 30 with 512 bytes that the stamped table lists, 640 with 6 KiB) take 63,569,920 bytes of host-visible c1 without `c1_full_vk.tsv` (64 KiB each) and 10,354,688 with it (940 packed in 2 banks of 4 MiB, the 30 listed with 64 KiB each): 16.3 %; the 300 of 768 bytes alone 19,660,800 bytes against one bank of 4,194,304. The allocator's shutdown line: peak 2 blocks, 128 MiB with 92.8 MiB in use without the table, 1 block, 64 MiB with 42.0 MiB in use with it.
